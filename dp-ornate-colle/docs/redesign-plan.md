# Redesign Plan — Dimpurr 个人主页视觉重做

> 范围：只改 `index.html` 的视觉与交互表现。信息架构、文案内容、`data/*.js`、图片资源一律不动。
> 硬约束保持：单文件、内联 CSS、vanilla JS、零依赖零构建；中英切换；xp 只排序不展示；设备按年份升序、null 显示 N/A；页脚四个链接内容不变；图片全部本地相对路径。

---

## 1. 设计方向

**关键词：白纸一样的底、呼吸感、一点淡蓝的凉意、衬线的温度。**

现在的问题是「深色高冷 + 机械等宽网格」，像展柜。新方向是「一本摊开的白色收藏手账」：
白底为主，用极浅的蓝灰色做分区衬底，卡片像贴在纸上的照片，圆角自然、阴影柔软、动效轻到几乎察觉不到。

- **白底 + 浅蓝灰分区**：body 纯白；intro 下方、收藏区、页脚之间用非常浅的 `#f6f9fc` 区块分隔，靠色块而非粗边框划分层次。
- **衬线做标题、无衬线做 UI**：现在 Playfair/Garamond 太正式（"端着"的主要来源）。换成 **Fraunces**（现代、暖、有手写感的衬线，只用于名字和区块标题）+ 系统无衬线栈（中文落到苹方/思源黑体系），UI 文案全部走无衬线，立刻"放松"下来。
- **圆角要"自然"**：不搞全站统一 8px/16px 的机械圆角。卡片用 `18px` 基础值，图片容器略小 `14px`，tabs 用胶囊形；个别重点元素（如 intro 区装饰）用非对称圆角（如 `24px 24px 24px 8px`）制造一点手绘感。全站圆角 token 化，控制在 3 档。
- **tab 配图标**：内联 SVG（零依赖），大 tab 用耳机/手机/游戏角色类线性图标，小 tab 可以纯文字。图标用 1.5px 描边线性风格，跟淡蓝点缀统一。

### 配色 token

```css
:root {
  --bg:        #ffffff;   /* 页面主底 */
  --surface:   #f6f9fc;   /* 分区衬底：极浅蓝灰 */
  --card-bg:   #fbfdfe;   /* 卡片图槽底：比 surface 更浅 */
  --ink:       #232d36;   /* 主文字：带蓝调的黑 */
  --muted:     #7d8b97;   /* 次要文字 */
  --faint:     #a8b4be;   /* 年份等三级文字 */
  --line:      #e4ecf2;   /* 分隔线：不用灰用蓝灰 */
  --accent:    #a9cbe8;   /* 点缀淡蓝：icon、hover、选中态 */
  --accent-ink:#5b8ab5;   /* 淡蓝上的可点击文字，保证对比度 */
  --shadow-card: 0 1px 2px rgba(35,60,90,.05), 0 6px 20px -8px rgba(35,60,90,.10);
  --r-lg: 18px;  --r-md: 14px;  --r-pill: 999px;
}
```

对比度自查：`--muted` on 白 ≈ 4.6:1（正文级达标）；`--accent` 只用于图形/装饰，正文级文字一律用 `--accent-ink`。

## 2. 布局与响应式策略

### 2.1 页面骨架（全断点通用）

```
┌─ 白底 ──────────────────────────────┐
│ intro（窄栏左对齐，max-width 560px）   │
├─ surface 浅蓝灰分区 ─────────────────┤
│ 大 tab（图标+文字，左对齐）            │
│ 小 tab（胶囊 chips，可横滑）           │
│ 卡片流（masonry / grid）              │
├─ 白底 ──────────────────────────────┤
│ footer 历代主页（小字横排链接）         │
└──────────────────────────────────────┘
```

语言切换按钮：保持右上固定，但改成胶囊白底描边小按钮，不再是黑底幽灵框。

### 2.2 容器宽度

现在 `max-width: 900px` 是"大屏显空"的根因。改为**分区容器**：
intro/footer 维持 `max-width: 640px` 阅读宽；收藏区容器 `max-width: 1280px`，2K/4K 下居中、两侧留白是设计的一部分而不是"空"。

### 2.3 两类图片混排：核心决策

素材盘点：
- 角色 31 张：原神 23 张 **2:1 横版**、绝区零 8 张 **1:1.6 竖版**（All 里混排）
- 设备 16 张：全部 **1:1 透明去背**

**方案选择：CSS 多列瀑布流（`column-count` + `break-inside: avoid`），只对角色区用；设备区用普通等宽 grid。**

理由：
1. 设备全是 1:1，等宽 grid 就是最优解，masonry 无意义。设备图槽给 `aspect-ratio: 1/1` + 浅色图槽底 + 内边距，透明去背图会显得很干净。
2. 角色区 2:1 和 1:1.6 高度差 3 倍多，等宽 grid 必然出现大量空洞或强行裁切；masonry 让每张图保持原始比例自然错落，正是这类"收藏墙"的标准解法。
3. 零 JS、零布局抖动：纯 CSS，图片加载前后不 reflow（每列宽度由 column-count 决定，高度随图自然撑开）。
4. 备选方案「grid-auto-rows + JS 计算 row-span」能保持**行优先**阅读顺序，但需要 JS 参与布局、窗口 resize 要重算、图片加载期会跳动——为了一个纯展示收藏页引入这些复杂度不值得（KISS）。

**代价与取舍（需要你确认，见 §5-1）**：CSS 多列瀑布流的填充顺序是**列优先**（先填满第一列再第二列），所以角色的 xp 倒序在视觉上变成"每列从上到下递减"，而不是"从左到右、从上到下"。xp 排序仍然生效、绝不展示数值，只是阅读动线变化。

### 2.4 断点表

| 断点 | 角色区列数 | 设备区列数 | 说明 |
|---|---|---|---|
| < 560px（手机） | 2 | 2 | 小 tab 横向可滑动；竖版立绘 2 列下高度可接受 |
| 560–900px（大手机/小平板） | 3 | 3 | |
| 900–1280px（iPad 横屏/laptop） | 4 | 4 | |
| > 1280px（2K/4K） | 5 | 5 | 容器 1280px 居中，列宽稳定在 ~230px，图不会糊 |

列宽稳定在 200–260px 区间：手机上不至于看不清立绘细节，4K 上也不会被拉伸得巨大空洞。grid-auto-flow: dense 不需要了（masonry 天然无洞）。

## 3. 动效（克制，参考 emilkowalski/skills 的规则）

只做三处，全部遵守「只动 transform/opacity、ease-out、150–250ms、stagger 30–60ms」：

1. **卡片入场 stagger**：tab 切换/首屏渲染时，卡片 `opacity: 0 → 1` + `translateY(8px → 0)`，每张延迟 40ms、250ms ease-out（`cubic-bezier(0.22, 1, 0.36, 1)`）。不阻塞交互。
2. **卡片 hover**：`translateY(-3px)` + 阴影加深 + 图片 `scale(1.02)`，180ms ease-out；**必须包在 `@media (hover: hover) and (pointer: fine)` 里**，避免触屏误触发。
3. **tab 选中态**：颜色过渡 150ms，小 tab 胶囊背景滑动（用 transition 不做 layout animation）。

全站 `prefers-reduced-motion: reduce` 时去掉位移、只保留 opacity 渐变。`transition: all` 一律禁止，写明属性。

## 5. 需要你确认的取舍

1. **masonry 的阅读顺序**（最重要）：接受列优先填充（xp 顺序按列读），换零 JS、无抖动的瀑布流？还是坚持行优先、接受引入一段 JS 布局计算？我推荐前者。
2. **字体换血**：Playfair/Garamond → Fraunces + 系统无衬线。Google Fonts CDN 沿用现状（现页就在用，不算新依赖）。如果你更想保留现在的字体也行，但整体气质会偏正式。
3. **intro 区装饰度**：我想在 intro 加一点点非对称圆角色块/装饰线做"手账感"，克制到近乎没有。如果你要绝对素净，我就只做排版不加装饰。
4. **大屏列数上限**：5 列 @1280px 容器（列宽 ~230px）。你的 4K 屏如果想更饱满可以 6 列，但单列会偏窄、立绘细节变小。默认 5。
5. **图标风格**：大 tab 配线性 SVG 图标是默认项；如果你其实想要纯文字的高级感，也可以去掉，视觉会更"编辑风"。

## 6. 暗色模式与偏好持久化（第二次迭代）

### 6.1 暗色配色思路

暗色版不是「把白色反相」，而是同一气质的夜景：柔和的蓝灰深处（`#161d26` 打底、`#1c2530` 分区），不纯黑、不高对比，点缀淡蓝提亮到 `#7ba7cd` 保证暗底上的辨识度。

关键决策：**暗色下图槽（`--figure-bg`）用与 surface 同族、再亮一档的冷中性灰蓝 `#27313d`**。整条明度层级是 bg `#161d26` < surface `#1c2530` < figure `#27313d` < control `#242f3c`，同族单色、每档亮度差很小——暗色要柔和，靠的就是「层级靠明度微差表达，而不是靠色相对比」。

曾被否掉的两个方案：
- **白/浅色图槽**（最初实现）：确实让深色去背图和白底卡池图「零处理即好看」，但实际效果是整页暗底上戳着几十块刺眼的亮白方块，暗色整体观感被破坏，一票否决。
- **去掉图槽、图片直接放卡片底**：去背图和卡池图的画幅差异会直接暴露（一个有底一个没底），网格失去统一的「瓷砖」节奏，收藏墙感觉散了。

取舍说明：当前图片素材是临时占位、以后会重新处理，因此图槽配色**以暗色整体观感为准，图片将就**——深色去背图在 `#27313d` 上对比度偏低是已知代价，等新素材（预计会按深色底重抠或加浅色描边）落地后自然解决，不为此退回白底。

### 6.2 跟随系统 + 手动优先

- 主题：默认读 `prefers-color-scheme`，并监听其变化实时跟随；语言：默认读 `navigator.language`。
- 用户一旦手动切换，写入 `localStorage`，之后以手动为准（系统变化不再覆盖）。
- 首帧 FOUC 防护：`<head>` 内联一段 3 行脚本，在 CSSOM 构建前把 `data-theme` 写到 `<html>` 上，暗色用户不会看到白屏闪一下。

### 6.3 论证：手动选择要不要记住？记在哪？

三个候选：

1. **不缓存（每次刷新回到跟随系统）**
   优点：实现最简、永远「智能」。缺点：对一个个人主页是真实痛点——很多人系统主题是日间、但逛网页时偏好暗色（或反过来）。不缓存意味着**每次打开都要重新点一下开关**，而个人主页是会被反复访问的页面，这个摩擦会重复发生。跟随系统只是好的「默认值」，不是好的「全部策略」。

2. **localStorage**
   优点：纯客户端、无过期概念、读写同步简单、`file://` 下也可用（本站主要用法就是磁盘直接打开）；隐私模式下抛异常，try/catch 静默降级为「不记忆」即可，不影响功能。缺点：跨浏览器/换设备不同步——但对个人主页这根本不算问题。

3. **Cookie**
   Cookie 的意义是「随请求发给服务端」。本站是纯静态页、没有任何服务端逻辑，Cookie 的每次请求都携带、过期管理、容量限制全是负担而无一处受益；且 `file://` 下 Cookie 行为不可靠。唯一可能的场景是将来上 CDN 做服务端主题渲染——那是引入服务端才需要考虑的事，与现状无关。

**结论：localStorage。** 它是「纯静态站记住用户偏好」的标准答案：零成本、零服务端、持久期合理、降级优雅。

附带决策：手动选择**永久生效**，不提供「恢复跟随系统」的 UI。理由：两个开关（日/夜、中/英）本身语义已经够直白，再加第三种隐形态（「自动」）会让一个个人主页的 UI 变复杂，违背 KISS；想恢复自动的用户清一下站点数据即可，这个成本可以接受。

## 7. 响应式零横向溢出自查（第三次迭代）

### 7.1 修复：intro 装饰块越界

**现象**：iPad（834px）出现横向滚动条，`.intro::before` 装饰色块（`position:absolute; left:-88px`）左边缘算出 x≈-55px，戳出视口左侧。iOS Safari 对 `body { overflow-x: clip }` 向 viewport 的传播与 Chrome 不一致，「先溢出再裁掉」不可靠。

**修复（根因，非裁剪）**：装饰块左偏移按断点收缩，永远不超过 `.intro-wrap` 的左内边距（`clamp(1.25rem, 4vw, 3rem)` + 居中边距），从几何上不可能越界：

```css
.intro::before { left: -20px; }                       /* ≤ min 内边距 1.25rem */
@media (min-width: 768px)  { .intro::before { left: -30px; } } /* ≤ 4vw@768=30.7px */
@media (min-width: 1400px) { .intro::before { left: -88px; } } /* 居中边距+48px ≥ 88px */
```

`body` 的 `overflow-x: clip` 保留为第二道防线，但不再依赖它。视觉效果：大屏完整出血、小屏贴边而不越界，手账感保留。

### 7.2 自查方法

headless Chrome 直接开窗最小宽度是 500px，无法测 390/430，因此用 **CDP（Chrome DevTools Protocol）** 驱动：`Emulation.setDeviceMetricsOverride` 模拟任意视口宽度，`Runtime.evaluate` 在页面内测量。脚本对每个宽度依次切换 2 个大 tab × 明暗 2 主题，共 8×4=32 组断言。脚本已收入仓库 `scripts/responsive-audit.mjs`（纯 dev 工具，与站点运行时无关），用法：

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless=new --remote-debugging-port=9222 --user-data-dir=/tmp/dp-cdp-profile about:blank &
node scripts/responsive-audit.mjs "file://$PWD/index.html"   # 全 PASS 退出码 0
kill %1
```

两个关键的测量认知：

1. **右溢出**：断言 `document.documentElement.scrollWidth <= clientWidth`。
2. **左溢出**：Chrome（LTR）**不把左侧溢出计入 scrollWidth**——已用 bug 版实测验证（`left:-88px` 时 scrollWidth 仍等于 clientWidth）。所以左溢出必须逐元素扫 `getBoundingClientRect().left < -0.5`；其中被合法 `overflow` 滚动容器（如小 tab 横滑 chips）裁掉的元素跳过。伪元素不在 DOM 树，`.intro::before` 单独用 `getComputedStyle(el, '::before')` 算左边缘断言。

**harness 灵敏度验证**：把 bug（`left:-88px` 全断点生效）喂给脚本，32 组全部 FAIL 且准确定位 `.intro::before L-68`（390px）/ `L-57`（834px），证明断言有效；修复版再跑全 PASS，结论可信。

### 7.3 自查结果（修复后）

|---|---|---|---|---|
| 390 (iPhone) | PASS | PASS | PASS | PASS |
| 430 (iPhone Max) | PASS | PASS | PASS | PASS |
| 768 | PASS | PASS | PASS | PASS |

### 7.4 小 tab 横滑容器专项检查

`.tabs-minor`（`overflow-x: auto`）是块级容器，宽度由父级决定，内部 chips（`flex: none`）超出时只在自身滚动区内滚动，**不会撑宽父级**——32 组断言中无任何 tabs-minor 相关越界，且其内部按钮的 rect 超出视口时被脚本正确识别为「被合法裁剪」而跳过，行为符合预期。

### 7.5 暗色图槽改色（同次迭代）

暗色 `--figure-bg` 从浅色 `#f2f7fb` 改为与 surface 同族、再亮一档的冷中性灰蓝 `#27313d`，并加 1px 同族描边 `--figure-line: #33404e` 补出瓷砖边界（暗底上明度差小，纯阴影不够）。理由与取舍见 §6.1。

## 8. 电影与动画收藏（第四次迭代）

新增两个大 tab：喜欢的电影（Movies I Like，35 条豆瓣 5 星）/ 喜欢的动画（Anime I Like，45 条 bgm 9-10 分），各配胶片/电视线性 SVG 图标，与设备、角色并列。

设计决策：

- **布局**：海报统一 2:3 竖版（420×593），比例一致就意味着等宽 grid 是最优解——复用设备区的 2/3/4/5 列断点，不需要角色区那种瀑布流。海报满幅裁切（`object-fit: cover`、无内边距），形成整齐的「海报墙」。
- **排序与分数**：数据层已按分数降序排好，渲染保持原顺序不再重排；`score`/`score2` 与角色 `xp` 同规——只排序，任何 UI 不展示。电影显示年份，动画无年份字段则不显示。
- **名称**：电影名是中文字符串直接显示；动画名 `{zh,en}` 跟随语言切换。`card()` 统一用 `typeof item.name === 'object' ? item.name[lang] : item.name` 处理。
- **小 tab**：这两个大 tab 只有一个分类，`minors.length <= 1` 时整行小 tab 不渲染（`display: none`），不出现孤零零的「全部」chip。
- **「查看完整清单」**：做成与大 tab 行右对齐的安静胶囊链接（`margin-left: auto`，窄屏随 flex-wrap 落到下一行），文字「完整清单 / Full list」+ 小箭头 SVG，不配 logo——豆瓣/bgm 的品牌色会打破页面单色层级，纯文字外链足够。仅当前 tab 配置了 `list` 时显示，切走即隐藏。
- **海报可点**：整张卡就是 `<a>`（`target="_blank" rel="noopener"`），直达豆瓣/bgm 条目页。为了不打扰静态视觉，可点性只靠两个已有线索表达：卡片 hover 浮起 + 图槽右上角浮出圆形 ↗ 徽章（`opacity 0→1`，仅在 `hover:hover` 设备出现）。键盘用户走原生 `<a>` 焦点，无障碍语义完整。

自查：`scripts/responsive-audit.mjs` 扩展为 4 tab × 2 主题 × 8 宽度 = 64 组断言，全部 PASS（零横向溢出）。

## 9. 游戏收藏 + 收藏区全宽化（第五次迭代）

### 9.1 新增「喜欢的游戏 / Games I Like」大 tab

40 条（Steam 20 + Switch 20），配手柄线性 SVG 图标，小 tab 为 全部 / Steam / Switch（复用现有 chips 机制）。

- **混排布局**：Steam 封面 2:3 竖版、Switch 封面 1:1 方形，「全部」里混排。两者都是竖向视觉权重（竖版 + 方形），复用角色区的 CSS 多列瀑布流（`masonry: true`），各保持原比例自然错落。Switch 方形封面满幅裁切，不需要设备区那种内边距图槽。
- **score / sub**：`score`（Steam 游玩小时数）与 xp 同规只排序不展示——数据已按时长降序排好，渲染保持原顺序；`sub`（"78h"）**显示**，游玩时长是有信息量的个人数据，与设备年份同级排版（`.s` 行）。Switch 的 `sub` 为 null 自然不显示。
- **可点性不一致**：Steam 条目有商店页 url，整卡为 `<a>` + hover ↗ 徽章；Switch 的 `url` 为 null，`card()` 的 `item.url` 条件使其自然降级为纯 `<div>`——不可点、无徽章、无手型以外的误导，同一网格里两种卡片视觉一致、交互诚实。
- **「完整清单」**：整个 games 大 tab 统一指向 Steam 个人主页（`g.list` 是大 tab 级配置，与小 tab 无关），Switch 没有可公开清单页，不为它单独处理。

### 9.2 收藏区全宽化

**问题**：收藏区容器 `max-width: 1320px` + 列数上限 5，超宽屏两侧大片空白。

**改法**：
- 收藏区（大 tab 行 + 小 tab 行 + 卡片流）删除 `max-width`，吃满视口宽，只留 `clamp(1.25rem, 4vw, 3rem)` 内边距；intro 与 footer 保留 1320px 阅读宽——文本行太长伤可读性，卡片流没这个问题。
- 等宽网格从固定断点列数（2/3/4/5）改为 `repeat(auto-fill, minmax(N, 1fr))`，瀑布流从 `column-count` 改为 `column-width`——两者本质相同：给列宽一个下限，列数随视口自动增长。下限分三档：`<900px: 150px`、`≥900px: 180px`、`≥1600px: 215px`，实际列宽被锁在约 150–250px 区间，不会被拉宽也不会挤窄。
- 参考表现：390px → 2 列；1440 → 6 列；2560 → 10 列；3440 → 14 列。四个大 tab 全部适用（角色/游戏瀑布流与设备/海报网格用同一档列宽下限，视觉密度一致）。

### 9.3 自查

`responsive-audit.mjs` 扩展为 5 tab × 2 主题 × 9 宽度（新增 3440 超宽）= 90 组断言，全部 PASS。

## 10. 去过的地方 + 视图切换机制（第六次迭代）

新增大 tab「去过的地方 / Places I've Been」（51 条，图钉图标），并引入全站第一个**视图切换**机制。

### 10.1 视图切换的位置与视觉

小 tab 行重构为 `.minor-row`：左边是筛选 chips（沿用现有机制，互斥），右边是一个**分段控件**（`.tabs-view`，整体胶囊容器 + 内嵌按钮），`margin-left: auto` 居右。筛选与视图是两种操作：筛选是散开的独立胶囊，视图是一个带边框的整体容器，一眼可区分。只有 places tab 显示视图切换，切走即隐藏。三视图：卡片（默认）/ 地图 / 时间轴。

### 10.2 三个视图

- **卡片视图**：横构图城市照 3:2 满幅裁切，`.pgrid` 列宽下限比竖版卡片略大（160/205/245px 三档）。标题=城市名，二级行=`segs` 时间段串（两行截断），三级行=国旗+国家+首访年份。`days`/`photos` 与 xp 同规——只排序（数据已排好），任何 UI 不展示。
- **地图视图**：**d3-geo（Natural Earth 投影）+ topojson-client + world-atlas 110m 国界**，三个文件全部 vendor 进 `vendor/`（含把 topojson 内联成 `world-110m.js`，`file://` 直开免 fetch），纯矢量、零网络、离线可用。颜色全走 CSS 变量（海洋 `--accent-bg`、陆地 `--figure-bg`、经纬网 `--line`），日夜切换零重绘。居住=实心点、旅游=空心点，左下角图例；点按弹卡（照片+名称+国家/首访+时间段），靠顶部的点弹卡自动翻转到下方。
- **时间轴视图**：横轴为首次到访时间（5 年刻度）。居住在上（条目少，标签两层总能放下）；旅游点按**月份在轴下条带内纵向散开**——2022 年 17 段旅行自然聚成一簇，密集本身就是信息。标签贪心两层避让，放不下的只留点：悬停有 `<title>` 提示、点击弹纯文字卡（无图，体积小，不会超出泳道被裁）。窄屏横向滑动（`min-width: 1700px`）。

### 10.3 依赖决策

打破「零依赖」惯例是有意识的：brief 明确允许挂库，优先级是「最好看、最合适」。选 d3-geo 矢量方案而非 Leaflet/MapLibre 的原因：无瓦片=完全离线+配色与站点 token 无缝贴合；Leaflet 底图瓦片要联网，离线降级难看。vendor 本地化（共 ~400KB）而非 CDN：这是个存档仓库，`file://` 直开也要能用。

### 10.4 自查

`responsive-audit.mjs` 扩展为 5 旧 tab + places×3 视图 × 明暗 × 9 宽度 = 144 组断言，全部 PASS。期间修了审计工具本身的一个误报：SVG 子元素的 UA 默认 `overflow:hidden` 裁的是 svg 视口而非页面，向上找裁剪容器时应跳过 SVG 祖先。

## 11. 角色图高度自适应 + 排序切换（第七次迭代）

### 11.1 角色卡：锁宽度、高度自动

卡池图比例差异大（原神 2:1 横版 / 绝区零 1:1.6 竖版），原先 `aspect-ratio` 锁高度必然裁切画面。改为去掉 figure 的 aspect-ratio，`img { width: 100%; height: auto }`——整图完整显示，瀑布流天然消化高度差。`tall` 的 contain/padding 补偿规则一并删除。

### 11.2 排序切换：按评分 / 按时间

**只给 Dim 点名的三个 tab**：glam（`rank`）、anime（`score`）、movies（`score`）。机制按 tab key 挂在 `SORT_KEY` 映射上，glam 由 Claude 接进 `MAJOR` 后自动获得按钮，无需再改逻辑。其他 tab 一律不出现。

- **交互**：单按钮在两模式间切换，按钮文字显示当前模式；排序状态是页级会话态，切 tab 保留。
- **视觉**：与视图切换明确区分——视图切换是「多按钮一个整体」的分段容器，排序是「单个幽灵胶囊按钮」（虚线描边 + 双向箭头图标 + 当前模式文字），放在小 tab 行右侧同一位置（两者按 tab 互斥，不会同时出现）。
- **评分排序**：按隐性分数键降序（稳定排序，同分保持数据原顺序，缺键排最后）。⭐ 分数本身永远不展示。
- **时间排序**：`year` 降序，null 排最后。
